# 语料问题全面分析

> 基于实测：审计器 `tools/kb_content_audit.py` → `00-索引/内容审计-all.md`、`_meta/content_audit.json`
> 范围：334 条唯一条目（记录 1824）

## 结论先行

| 指标 | 数值 | 含义 |
|---|---|---|
| 可用语料（相关 + 正文完整） | **170 / 334（51%）** | 一半语料对目标分析是负资产 |
| 不可用（空 / 过短 / 摘要残文） | **62（19%）** | 喂给 AI 只会污染聚类 |
| 相关性可疑（无项目信号/资源清单/泛媒体/大厂） | **145（43%）** | 用户指出的「很多和项目无关」 |
| 正文被硬截断（Exa 8000 字符） | **17** | 用户指出的「原文不全」 |
| RSS 摘要残文 | **31** | 同上 |
| 历史深度 | **1 天** | 无法做任何趋势分析 |
| 跨渠道重复检测 | **仅 2 条** | 因 138 条无 project_url，检测能力被限制 |

**根因归纳**：现有体检（`kb_audit.py`）只回答「**能不能取到数**」，从不回答「**取到的是不是想要的东西**」。
于是「渠道能取到数」被默认等价于「渠道产出目标语料」，噪声与残文一路入库。

## 一、用户指出的问题：与「独立开发项目」无关

### 证据（按渠道，可用/总数）

| 渠道 | 可用/总 | 主要噪声类型 | 实例 |
|---|---|---|---|
| `apple_rss` | **0/18** | App Store 榜单，13 条大厂 | `Muse from Meta`、`ChatGPT — OpenAI`、`Five Guys`、`Vinted`、`TikTok Pro` |
| `sspai` | **1/10** | 泛科技/生活媒体 | 《你的脸红是什么红：了解玫瑰痤疮》《8月音乐精选》《城市漫步指南｜威海初秋》《watchOS 27 新变化》 |
| `c1c7` | **3/17** | 资源清单/名录，不是项目 | `Awesome Indie`、`Failory`、`Starter Story`、`MicroConf 视频`、`Stripe Atlas Guide`、`NomadList`、`利器` |
| `hn_front` | **9/19** | 泛技术话题，与做产品无关 | 《What Zig felt like, coming from Rust》《A graphical desktop for the ZX Spectrum》《Human brain is two separate organs》 |
| `github_new` | **7/28** | 召回 `awesome-*` 资源清单 | `awesome-side-project`、`awesome-indiehackers`、`Best-Micro-SaaS-Tools` |
| `betalist` | **5/18** | 抓到的正文是 BetaList 页面片段，无作者/指标/时间 | `Gb7 Meetup`、`Zapters`、`1Presence` |
| `reddit` | **14/37** | 泛话题帖（`Do you like the mechanic and visuals?`） | — |
| `bilibili` | **7/20** | 标题相关但正文只有一句视频简介 | 《独立开发两种赚钱方式！》→ 正文 `更多内容请前往社区 + 一个链接` |
| `exa_discovery` | 14/15 | 相关性 OK，但召回偏 Steam 独立游戏发售新闻，与「软件/SaaS」主线错位 | — |

### 根因（三层，都不是「抓取 bug」）

1. **渠道定位错**：`sspai` 是泛科技媒体、`hn_front` 是技术话题榜、`apple_rss` 是 App Store 榜单。
   它们**能稳定取到数**，但产出物天然不是「独立开发项目」。
   → 现流程只体检「取数可用性」，没有「产出相关性」这道门。
2. **召回式查询缺负向约束**：`topic:indie-hacker` 会命中 awesome-list；Exa 语义查询会命中游戏新闻。
   → 有 `min_points`/`min_score` 这类**热度阈值**，但没有**主题白名单/黑名单**。
3. **策略变更不回溯**：`apple_rss` 的大厂过滤是 R1 之后加的，但 18 条历史条目仍留在库里
   （`latest_by_item` 只看历史，不重跑过滤）。与「粘性缺口」同源：**策略更新不会回溯旧数据**。

### 影响

- 项目热度被榜单/大厂产品稀释（`10-项目/` 里 18 条 App Store 条目把「项目」概念污染成「任何 App」）
- 后续任何聚类/统计都会把这些算进去（赛道分布、定价分布失真）
- 用户读库时的第一印象就是「跟项目无关的很多」——信任成本

## 二、用户指出的问题：原文并不全

### 证据

| 缺陷 | 条数 | 渠道分布 |
|---|---|---|
| 空正文 | **26** | apple_rss 18、其余零散 |
| 正文 <200 字符 | **32** | bilibili（视频简介）、betalist（页面片段） |
| RSS 摘要残文 | **31** | **sspai 7**、c1c7 5、其余零散 |
| Exa 8000 字符硬截断 | **17** | hn_front 12、hn_show 8、lobsters 7、c1c7 3 |
| HTML 未清理 | **54** | github_new（README 混排）、sspai（feed 带 `<a>`） |

**残留痕迹（铁证）**：

```
sspai 正文尾部：……本作为《哆啦A梦》电影系列第46部作品，森山瑠潮执导， ...<a href="https://sspai.com/post/114716" target="_blank"
sspai 正文尾部：……今年我们也很荣幸邀请到老朋友飞傲，为本栏目冠名。飞傲目前拥有品牌以音乐发烧友为 ...<a href="https://sspai.com/post/114555" target="_blank"
hn_front 正文尾部：……Also, Claude doesn't specify a year, but smuggling\n\n# mindbox77/zxdesk     ← 恰好 8000 字符
```

### 根因（四层）

1. **RSS 渠道拿的是摘要，不是全文**
   `adapter: rss_atom` 直接取 feed 里的 `<description>/<content>` 就入库。
   `producthunt` 侥幸命中 `content:encoded`（含全文）；`sspai` 的 feed 只有摘要 → 入库即残文。
   → 没有「feed 是摘要型 → 二次抓原文页」这一步。
2. **Exa 单次上限 8000 字符，且不标记**
   `kb_collect.enrich_generic(..., max_chars=8000)`。超过就砍，`comments_truncated` 有标记机制，
   但 **`body` 没有对应标记** → 直接违反 skill 的硬约束「截断必须标注，不许静默截断」。
3. **schema 承诺与实物不符**
   `_meta/schema.json` 里 `body` 的描述是「**正文全文**。来源优先级：平台 API 正文 > README > Exa web_fetch > 空」，
   实际可能是「RSS 摘要 / 页面片段 / 8000 字符截断」。下游 AI 无法区分「这是全文」还是「这是开头」。
   → 缺 `body_completeness` 字段。
4. **元数据渠道与语料渠道混装**
   `apple_rss`（空 body）、`bilibili`（一句简介）合计 38 条，本质是「有元数据、无正文」的**信号**，
   和真语料放在同一层，拉低整体「正文完整率」，也让人误判库的质量。

### 影响

- 做「痛点聚类」时，截断的文章会让 AI 只看到开头 → 结论偏向标题
- 定价/收入类分析尤其致命：数字常出现在文中后段，8000 字符前往往还没有
- 用户明确要看原文时，库里给不出

## 三、其它问题（本次审计发现，用户未提）

### 3.1 【严重】历史深度只有 1 天 → 趋势类分析彻底做不了

- 证据：334 条 `captured_at` **全部是 2026-09-20**；`published_at` 跨度虽到 9-10，但每渠道只取当前窗口的 Top N。
- 后果：`10-项目/` 的「观测历史」表同一天堆了 N 行，**没有跨天对比**；「哪个赛道在升温」「上线节奏」这类问题无数据可答。
- 根因：采集只取「当下热门」窗口（reddit 7 天、github 14 天、HN 近 2 天），从没做过**历史铺底**。

### 3.2 【严重】有原料没产品：库内零分析产物

- `40-方法论/` 只有 README；`00-索引/` 只有台账、诊断、审计 —— **没有任何洞察**。
- 用户目标是「方便后续 AI 进行分析」，现状是「原料仓库，分析全靠临时提问」。
- 缺：赛道分类、痛点聚类、定价分布、上线/失败复盘、周报。

### 3.3 无主题/赛道维度 → 无法按赛道切片

- 209 条有 tags，但都是**渠道标签**（`r/SideProject`、`us-top-free`、分区名），没有赛道标签。
- 后果：「AI 工具赛道最近怎么样」无法回答；统计只能按渠道切，不能按题材切。

### 3.4 `kind` 与目标目录不对应

- `kind=method` **15 条**（c1c7 的教程/复盘类）没有对应 writer → 落进 `10-项目/`；`40-方法论/` 空。
- `kind=project` **70 条**里掺了 `Awesome Indie`、`Starter Story` 这类**资源清单**（不是项目）。
- → 分类定义了但没落地，比没有分类更误导。

### 3.5 跨渠道同项目未合并，热度被低估

- 仅检出 2 组（HN+Lobsters 同链接）。但 **138 条无 `project_url`** → 匹配能力被卡死，真实重复率应显著更高。
- 后果：同一项目在 HN / Reddit / PH / BetaList 各算 1 条，「热度」失真；无法回答「哪个项目被多渠道同时讨论」。

### 3.6 评论覆盖严重偏斜 → 「用户反馈/痛点」维度不可用

- 有评论：`hn_show`、`hn_front`、`reddit`、`lobsters`、`devto`
- 零评论：`producthunt`（需 GraphQL token）、`v2ex`（sov2ex 不给回复）、`bilibili`、`github_new`、`c1c7`、`betalist`
- 痛点/反对意见主要来自评论 → 只有 5 个渠道有，且都是海外的。

### 3.7 中文语料薄且退化

- `lang`：en **262** / zh **72**（21.6%）
- 且中文那 72 条里：`sspai` 7 条残文 + 5 条不相关、`bilibili` 13 条不可用 → **真正可用的中文语料约 45 条**
- 小红书 / X 未解锁；掘金详情 API 不可用（已探明）
- → 国内独立开发的观察能力明显弱于海外

### 3.8 时间字段不规范

- `published_at` 缺失 **73**；且出现 `Fri, 18 Se` 这种 **RFC822 未解析**的值（apple RSS 的 `releaseDate`）。
- 后果：按时间排序/画时间线会出现错位，无法做「上线节奏」分析。

### 3.9 `metrics` 跨渠道不可比，且 120 条全空

- 指标名各异：`rank`（Apple）/ `score`（Reddit）/ `play|danmaku|favorites`（B站）/ `points`（HN）/ 空。
- **120 条（36%）无任何指标** → 没法做「热度排序」，也没法做趋势。
- 命名也不统一（HN 用 `points`，Reddit 用 `score`，语义相同）。

### 3.10 `body_format` 不统一、HTML 残留

- `text` 195 / `markdown` 139 混用；54 条含未清理 HTML 标签（README、RSS feed）。
- 影响：喂给 AI 时格式噪声、token 浪费；`##` 与 `<h2>` 混排。

### 3.11 无导航层

- 334 个语料页散在 `20-语料/posts/<渠道>/<日期>/`，没有 MOC / 索引页。
- Obsidian 里只能靠搜索或 dataview；「按赛道看」「按热度看」都做不到。

## 四、修复方案（按优先级）

### P0 — 阻断分析目标，必须先修

| # | 动作 | 落点 | 验收 |
|---|---|---|---|
| P0-1 | **正文完整度治理**：① `rss_atom` 增加「摘要型 feed → 二次抓原文页」；② `enrich_generic.max_chars` 8000 → 40000 且**记录截断标记**；③ schema 加 `body_completeness`（`full/summary/snippet/metadata_only`）+ 存量回填 | `kb_collect.py`、`schema.json`、`kb_backfill.py` | 截断条数 17→0 且全部带标记；摘要残文 31→<5 |

## 五、明确不建议做的

1. **不要用 LLM 逐条判相关性**：334 条还行，铺底后会到上万条，成本不可控。用「规则 + 渠道门禁 + LLM 抽检校准」。
2. **不要靠开大 `limit` 解决「不够全」**：噪声会同比例放大。宁可 5 个渠道 × 50 条干净，不要 15 个渠道 × 200 条混杂。
3. **不要删历史数据**：`90-原始/` 不可变。不合格的进 `80-归档/` 或标 `relevance: reject`，保留可回溯性。
4. **不要为「中文覆盖」硬接泛媒体**：`sspai` 证明「中文 + 能取数」不等于有用。优先小红书/X/掘金/V2EX 这类**开发者聚集**渠道。

## 六、与已修问题的关系

前五轮修的是「**取数完整性**」（缺口、截断、去重、孤儿页），本轮暴露的是「**内容质量**」——
两个正交维度。取数全 ≠ 内容可用：现在取数缺口只剩 2 条，但可用语料只有 51%。
后续自动化流程必须补一道 `kb_content_audit` 内容门禁（已加入 skill）。
