## 二、原始问题的根因

### 2.1 「很多内容与项目无关」

根因是**只有一道门禁**：`kb_audit` 只管「能不能取到数」，没有门管「取到的是不是想要的」。
于是「渠道能稳定取到数」被默认等价于「产出目标语料」，泛科技媒体、App Store 商业榜、
awesome-* 资源清单一路入库。

按渠道实测的可用率（修复前）：`apple_rss 0/18`、`sspai 1/10`、`c1c7 3/17`、
`github_new 7/28`、`hn_front 9/19`。

**修复**：
1. 新增第二道门禁 `tools/kb_content_audit.py`（内容质量审计，与取数门禁正交）。
2. 新增 `_meta/rules.yaml` 主题准入规则（全局 + 渠道级 排除/必需 正则），
   在采集时执行，**分两段**：排除规则在补正文之前跑（省预算），
   主题词在补正文之后跑（判定才准）。
3. 停用 5 个内容层不成立的渠道：`apple_rss`（大厂商业榜）、`sspai`（泛科技/生活媒体）、
   `hn_front`（综合技术头条）、`lobsters`（纯技术社区）、`uneed`（连续空）。
   每条都在 `channels.yaml` 写明**原因 + 复活条件**，不静默删除。
4. 新增 `tools/kb_prune.py`：规则只作用于新进语料，**存量**必须重判归档。
   已归档 107 条 → `80-归档/`，带 undo 清单可原样搬回。

### 2.2 「原文不全，很多是点击查看全文」

根因有三条，且互相叠加：

| 根因 | 后果 | 修复 |
|---|---|---|
| Exa 取正文上限写死 8000 字符，**且超限不标记** | 17 条刚好 8000 字，正文被拦腰砍断却看着像完整 | `FULLTEXT_MAX_CHARS=40000` + 命中上限写 `extra.body_truncated` |
| 回填队列只判 `len(body) >= 120` | RSS 给的 300~600 字**摘要**被当成「已有正文」，永远不进回填队列（31 条） | 改用 `body_completeness()`，只有 `full` 才免除 |
| 历史被 8000 砍断的条目身上没有新标记 | 长度足够骗过「够长就算完整」，判成 full 后仍不回填（14 条） | 新增 `truncated_at_cap()`：长度贴上限**且**结尾像话没说完才算 |

**修复动作**：回填 385 条正文 + 38 条评论缺口。

## 三、修复过程中发现并修掉的**我方判据错误**

这一轮最有价值的部分 —— 有几个「看起来是语料脏」的问题，实际是**判据错**：

| # | 现象 | 错判 | 真相 |
|---|---|---|---|
| 1 | `betalist` 的 "Zapters"/"Aria"/"Campaignstack"（正文 500~900 字）被判「无项目信号」 | 假阳性 | BetaList **只收产品**，条目存在本身即证明是项目 → 渠道语义问题 |
| 2 | `reddit` 的 "One thing selling software to restaurants is teaching me" 被判无关 | 假阳性 | 词表只有「发布词」（MRR/pricing），缺**创始人经营词**（裸 SaaS/customer/selling） |
| 3 | `hn_show` 41/42 被判「无项目信号」 | 假阳性 | 「Show HN」前缀即自我发布声明，被当作无关键词 |
| 4 | `bilibili` 被记 unusable 10 条 | 假阳性 | 信号层渠道本就不产出正文，拿正文层尺子量它 |
| 5 | `hn_front` 的 "How to Write with an LLM" 混进「可用」 | 假阳性 | 正文参与主题匹配 → 长正文里**顺带**出现 launch/startup 即命中，等于没过滤 |
| 6 | 审计器只读 `90-原始/` | 掩盖修复 | raw 是只追加的重放底座，归档不改它 → 可用率永远卡在 51% |
| 7 | 报告「历史深度 1 天」 | 掩盖修复 | 混用了 `captured_at`（采集日）与 `published_at`（发布日），刚做完 90 天铺底仍显示 1 天 |

对应的判据修正已写进 `tools/kb_content_audit.py` 与 skill 的「判定纪律」段，
并在代码注释里保留了**为什么**（避免以后有人「顺手」改回去）。

## 四、还没解决的问题（诚实清单）

### 4.1 元数据缺口（最大）

| 缺口 | 条数 | 性质 |
|---|---|---|
| 无指标（`metrics` 空） | 94 | 主要体现在 `c1c7`/`devto` 等无指标渠道；跨渠道**不可比** |
| 无项目链接 | 73 | 见 4.3 |
| HTML 未清理 | 62 | GitHub README 与部分 RSS 正文残留标签 |
| 缺作者 | 51 | 多为 `lobsters`（已停用）/`bilibili` 等 |
| 缺发布时间 | 45 | 45 条完全无发布时间 → 时间序列分析排除它们 |

### 4.2 新扩语料的完整性

历史铺底新增 435 条，其中 27 条正文取不到（已记死信账本）、42 条 `hn_show`
属结构性不可得。**可用率因此被拉低**，需要再跑 1-2 轮回填补齐。

评论覆盖仍偏窄：只有 `hn_show`/`reddit`/`lobsters`/`devto` 等少数渠道抓评论。
「痛点/需求」类分析若只看正文，会漏掉评论区里更真实的表述。

### 4.3 `project_url` 对部分渠道**结构性不可得**

`producthunt`(40/40)、`betalist`(17/18)、`exa_discovery`(8/9) 至今缺 `project_url`，
不是代码 bug，而是数据源限制：

- ProductHunt 的 RSS 正文里只有回指 `producthunt.com` 的链接（带 utm），**不含产品官网**；
- BetaList 经 Exa 抽取的正文里 **0 个链接**（Exa 丢了 `href`）。

**代价**：这些条目**不参与跨渠道归并** → 跨渠道强信号只有 3 个，
这个数字明显偏低不是「真的没有强信号」，而是**归并键缺失**。
要真正解决得抓页面 HTML 提外链，属下一轮工作。

### 4.4 剩余可用率偏低的渠道

| 渠道 | 可用/条目 | 主要问题 |
|---|---|---|
| `c1c7` | 2/7 | 中文名录，混着项目/资源站/人物 |
| `reddit` | 60/96 | 讨论型，仍有 32 条相关性可疑 |
| `github_new` | 41/66 | 随机仓库多，21 条相关性可疑、13 条资源型 |
| `devto` | 3/5 | 样本太小 |

### 4.5 结构性局限（不是「待修」，是设计边界）

- **中文语料偏薄**：主渠道以英文社区为主，中文仅 `v2ex`/`c1c7`/`bilibili`。
- **信号层不可做正文分析**：`bilibili`(16)、App Store 类只有元数据。
- **`c1c7` 资源型条目**（Failory/Starter Story 这类案例库）价值在「作为参考源存在」，
  而不在「作为项目语料」——目前按无关归档，其索引价值未被单独利用。
