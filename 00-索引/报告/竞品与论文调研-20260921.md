# 高星竞品与最新论文调研：本库是已命名的模式，缺的是语义 lint

> 起因：用户问「除了收集信息，我还想确认项目是否适合独立开发者、是否适合我，这部分该放当前项目还是独立出来」
> → 追问「调研高星竞品与热门论文，分析当前项目是否合理并优化；并分析语料是否符合预期，
> 对『只收到文章一小部分』『语料与预期不符』给出解决办法」。
>
> 调研通道：agent-reach（GitHub API 搜索 / Exa 网页语义搜索 / arXiv）。取数时间 2026-09-21。
> **本地实测口径**：`90-原始/*.jsonl` 27 个分片、6241 条观测记录 → 按 `item_id` 取最新得 **1732 唯一条目**；
> `live_only`（在库可消费）**1615** 条。所有比例的分母均为 1732 或 1615，文中逐处标注。

---

## 一、结论先行（三句）

1. **架构是合理的，而且不是我们发明的** —— Karpathy 2026-04 把「LLM 增量维护 Markdown wiki」命名为
   **LLM Wiki 模式**（gist 5,000+ star），衍生项目已过 15k star。我们的三层 / 三操作 / 两文件**逐条对得上**，
   属于独立收敛到同一解，这是设计合理性的最强一类证据（不是「我们觉得好用」）。
2. **真正的缺口只有一类，且不在采集侧**：模式的三个操作里 **Ingest（采集）与 index/log（账本）我们做得比原模式更细**，
   唯独 **Lint 只做了「结构性 lint」（计数/断链/漂移），完全没有「语义 lint」（页面间矛盾、被新来源取代的过期论断、
   概念被提到却没有自己页面）**。这是本库当前唯一的结构性欠账。
3. **「只收到文章一小部分」在数据上不成立**：正文 <200 字符的条目 **144/1732 = 8.3%**，
   其中 85 条已入死信账本（结构性）、4 条在回填队列、真·可抓未抓仅 **77 条且以视频/商店页为主**。
   真实的失败模式不是「抓得少」，而是**「判死得太早」——死信账本 270 条里 248 条的判死理由与实际尝试不一致**。
   本轮已修其中两类。

## 二、高星竞品：我们的架构是一个「已被命名的模式」

### 2.1 对表：本库 vs LLM Wiki 模式

Karpathy 的 [llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)（2026-04-04，5,000+ star / 5,000+ fork）
给出三层 + 三操作 + 两文件。逐条对表：

| 模式要求 | 本库实现 | 判定 |
|---|---|---|
| **Raw sources 不可变，是唯一事实源** | `90-原始/<渠道>/<日期>.jsonl`，只追加、口径变化只加新字段 | ✅ 完全一致 |
| **Wiki 层由 LLM 生成并维护** | `20-语料` / `10-项目` / `30-人物` / `40-方法论`，全部脚本生成、禁止手改 | ✅ 一致（且比模式更严：可再生成性有硬门禁） |
| **Schema = AGENTS.md，是「让它成为纪律维护者」的关键配置** | 根目录 `AGENTS.md`：分层、字段、命令、六条红线、五条不能下的结论 | ✅ 一致，粒度更细 |
| **Ingest** | `kb_collect` → 语料页 + 实体页 + 观测历史 | ✅ 超额（模式里 ingest 是人工触发的对话动作，我们是流水线） |
| **Query**：答案可归档回 wiki 成为新页面 | 报告进 `00-索引/报告/`，按日期命名、可重建 | ⚠️ **半实现**：答案产出了，但没进检索面（见 §5.2） |
| **Lint**：矛盾 / 过期论断 / 孤立页 / 概念缺页 / 缺交叉引用 / 数据缺口 | 八项不变量：①计数平衡 ②缺项目页 ③缺 url ④断链 ⑤路径漂移 ⑥孤立语料 ⑦project_url 合法性 ⑧共用页 | ⚠️ **只覆盖「结构」，缺「语义」**（见 §5.1） |
| **index.md**（内容目录：每条一链接 + 一句话摘要） | `00-索引/浏览.md` + Bases 视图（属性过滤，但**没有逐条摘要**） | ❌ 未建（我们 2026-09-20 调研已识别为 B1 并暂缓） |
| **log.md**（追加型、前缀可 grep） | `00-索引/运行日志.md` + `_meta/runs/*.json`（保 80 份） | ✅ 更细 |
| **「wiki 就是一个 markdown git 仓库」** | `.git` → GitHub `KOIYC/CollectProjectAndDetails` | ✅ |

**我们比这个模式多出来的东西**（模式里完全没有）：`seen.json` 去重账本 + `content_hash` 内容指纹、
`body_cache` 只增不减缓存、`backfill_dead` 死信账本、`backfill_queue` 待回填队列、
归档 undo manifest、八项不变量。也就是说：**原模式只管「wiki 长什么样」，我们把「语料怎么进得来、错了怎么修、判废了怎么捞」也建了账。**
这是本库相对所有同类项目的真优势，应当在文档里被明确声明，而不是埋在工具里。

## 三、最新论文（2026-04 ~ 2026-09）：七篇，逐篇只留「对我们的直接用法」

### 3.1 SARC-DQ：静默证据缺陷与「谓词覆盖」——最贴的一篇

**arXiv [2607.26313](https://arxiv.org/abs/2607.26313)，2026-07-28，cs.SE。**
核心论断（引用原文语义）：

- **最危险的缺陷是 metadata-borne**：「一个过期的价格、一条被取代的记录，在载荷里完好无损，只被 **freshness / lineage / provenance** 出卖」。
- 「**这样的缺陷永远不会进入 agent 的上下文，而 agent 无法怀疑它看不见的数据**。」
- 在定价补货基准上，**能力充分的 agent 有约 60% 的概率把注入的元数据缺陷静默转成昂贵动作，且数据质量告警为 0、行为怀疑标记与随机无异（AUC ≤ 0.50）**；跨越约 15 倍推理价格的四个模型档位，这个比例**保持平坦——能力买不到怀疑**。
- **缓解效果完全取决于两件事**：**enforcement placement（门禁放在哪）** 与 **predicate coverage（谓词覆盖到什么）**。「元数据感知的前置门能全额挽回它谓词覆盖到的损失，**而对其谓词未覆盖的信号一点也挽回不了**」。
- 结论句：**「证据完整性是一条系统轴，与模型能力不同的另一条轴。」**

**对我们的直接用法（三条，全部命中）**：

1. **把「元数据缺陷」立为独立缺陷类**，与「内容缺陷」并列。我们现在的门禁全在内容上（正文长度/相关性/截断），
   而本库最大的缺陷恰好是元数据的：`published_at` 缺失 107 条（6.6% of 1615），且 5 条是字面量 `'N/A'`、60 条是未归一化的 RFC822。
   这些记录的**载荷完好、不报错、能通过所有内容门禁**，只有时间轴一查就废。
2. **门禁位置**：我们现在的顺序是「先写库 → 再 `kb_content_audit` 审计」= **下游补救**。论文的结论是下游补救只在谓词覆盖内有效。
   → 应把**可判定的元数据规范化与契约检查前移到写入前**（`kb_collect` 写页之前）。
   本轮已把 `pub_day` 的归一化前移到采集端（`kb_collect` 写入时就归一），属于这一条的最小实现。
3. **谓词覆盖要显式建模**：我们的「谓词」就是渠道 `profile` 表。**未被 profile 覆盖的情形会同时在两个账本里消失** ——
   实测 43 条（bilibili 25 + apple_rss 18）长期既不在回填队列也不在死信账本。本轮已把它们明账化（§4.4）。

### 3.2 FLUX：行级切除优于整篇拒绝——上限截断的正解

**arXiv [2603.13972](https://arxiv.org/abs/2603.13972)。** 单一设计原则：
**「在任何可行处优先做文档内行级切除，而不是整篇拒绝」**。DCLM / FineWeb 在多数阶段做**二元整篇判决**，
提高精度但系统性地丢掉「偏噪声文档里的高价值内容」。FLUX 结果：**去重后比 DCLM 多保留 9.7% token、比 FineWeb 多 11.1%，同时在 530M 规模上聚合分更高** —— 保留率与质量**不是**基本权衡。

**对我们的直接用法**：我们的正文处理在撞上限时是**整条硬切**（`FULLTEXT_MAX_CHARS = 40000`，实测 27 条被标记 `body_truncated`，
历史 8000 档另有存量）。论文给的正解是「**切除/保住能保的部分**」而非「要么全文要么丢」。
具体到我们：撞顶条目应做**分段续取**（记住 offset，下一轮从截断点继续），而不是在同一上限上反复尝试。
这与 §3.5 的截断论文互相印证。

### 3.3 CuraWeb：单目标过滤会收窄分布——我们的「相关性」是单目标门

**arXiv [2607.22662](https://arxiv.org/abs/2607.22662)，2026-06-29。** 主张从「线性剪枝」转向
**质量 / 冗余 / 多样性联合优化**：先训专用模型给全部数据打多维信号（质量分 + 领域标签），
让这些属性**贯穿整条流水线**做漏斗监控。两个技术点值得我们抄：
- **域感知阈值**（domain-specific thresholds）替代统一阈值 —— 防止数学/代码这类严谨领域的高价值样本被误删；
- **软语义去重**（加权投票累积惩罚分，超阈值才判冗余），把最高相似区间的**误判率从 37.5% 降到 28.03%** —— 硬阈值会过度过滤「天然术语密集」的领域文档。

**对我们的直接用法**：我们只有**单目标**（相关性）判定，没有多样性/冗余维度。
后果可测：`reddit` 相关性可疑 89 条、`github_new` 13 条 —— 都是「按单一尺子量、边界样本被一刀切」。
**最低成本落地**：把「域感知阈值」的思路用到渠道画像上（我们已经有 `profile`，只是没有按渠道调阈值），
而不是全库统一 `BODY_MIN=120`。

### 3.4 FOLD：面向「持续演化数据集」的在线模糊去重

**arXiv [2606.03001](https://arxiv.org/abs/2606.03001)，2026-06-02。** 大规模演化数据集上的**在线**模糊去重（ANN 检索）。
旁证：`SemHash-LLM`（[2607.01601](https://arxiv.org/html/2607.01601v1)，2026-07-02）多粒度语义哈希、`SemDeDup`（[2303.09540](https://arxiv.org/html/2303.09540v3)）语义去重。

**对我们的直接用法**：我们的去重只有**精确 `content_hash`**（`seen.json`），没有近似去重。
已知代价写在 `AGENTS.md` 第 4.6 条：`projecthunt`/`betalist`/`exa_discovery` 的 `project_url` 结构性不可得
→ **跨渠道同一项目无法归并** → 被重复计为独立观测。健康检查 ⑧ 现在报「共用项目页的条目组 9 组／18 条」，
说明归并已经在发生但只靠 `project_url` 这一个键。**FOLD 是这条线的现成方法**：用标题 + 域名做近似键，
补上「无 project_url 时的归并」。风险：误归并会制造假强信号，须先做只读评估。

### 3.5 Distractor-Aware Truncation：截断导致的信号丢失 ≠ 长度效应

**arXiv [2608.03297](https://arxiv.org/html/2608.03297)，2026-08-04。** 把「上下文长度效应」与「**信号丢失**」解耦，
指出长上下文基准上的退化常来自**截断本身**，而不是长度。旁证：`Long Context vs. RAG`（[2501.01880](https://arxiv.org/html/2501.01880v1)）。

**对我们的直接用法**：正是我们 40000 / 历史 8000 两档截断的问题。**修法不是加长上限，是不要截断信号**（分段 + 保留 offset + 显式标记）。
我们做对的一半：`body_truncated` 标记 + `truncated_at_cap()` 双档探测（78000/40000 都查）—— 这点比论文里很多基准做得诚实。

### 3.6 正文抽取的 Pareto 前沿：抽取器该按基准选，不该按默认

- **Dripper**（KDD 2026，[dl.acm.org/10.1145/3770855.3817915](https://dl.acm.org/doi/10.1145/3770855.3817915)）：**token 高效的主 HTML 抽取**，用轻量 LM。
- **Pulpie**（[github.com/feyninc/pulpie](https://github.com/feyninc/pulpie)）：「清洗网页的 Pareto 最优模型」。
- **WCXB**（[2605.21097](https://arxiv.org/html/2605.21097v1)）：**多类型网页内容抽取基准**。
- **Readability vs Trafilatura vs jsdom 2026 基准**（BulkMD）：三种经典抽取器的横向对比。

**对我们的直接用法**：我们的正文抽取是 `direct_fetch`（stdlib 自写 HTML→text）→ Exa 兜底，**从没有用任何抽取基准来选过**。
`kepano/defuddle`（9,464 star）是现成组件。**建议动作**：拿本库已抓到的正文做一次小规模对照（抽 20 条同时用三档抓，
比正文长度 + 首尾完整度），把「抽取器选型」从直觉变成有据。这是低成本、可证伪的改进。

### 3.7 LLM-as-judge「可靠但未必有效」——反向印证我们不用 LLM 判相关性

**Reliability without Validity: A Systematic, Large-Scale Evaluation of LLM-as-a-Judge Models，arXiv [2606.19544](https://arxiv.org/abs/2606.19544)，2026-06-17。**
旁证：**Beyond Accuracy: LLM Variability in Evidence Screening**（[2604.27006](https://arxiv.org/html/2604.27006v1)，2026-04-29）—— 证据筛选场景下 LLM 的变异性。

**对我们的直接用法（这条是反向证据，必须说清）**：我们的相关性判定用**规则/正则 + 渠道画像**，**没有**用 LLM judge。
好处：绕开了 validity 与变异性问题，判定可复现、可审计、零成本。
代价：**假阴性**（该收的被规则漏掉）。
正确解法不是「换成 LLM」，而是论文 §3.3 的双轨：**规则守高精度、LLM 只用于规则边界样本**，
并且判据必须可回测（我们有 `drop_sink` 丢弃账本，正好是回测假阴性的现成样本源）。当前不建议动。

### 3.8 旁证：数据溯源标准已经成熟到有规范

**OASIS Data Provenance Metadata v1.0**（[docs.oasis-open.org/dps/prov-meta/v1.0](https://docs.oasis-open.org/dps/prov-meta/v1.0/csd01/prov-meta-v1.0-csd01.pdf)）、
`UnespDataLens-RM`（[2609.08184](https://arxiv.org/abs/2609.08184)，2026-09-08，治理/质量/溯源的参考模型）、ISO 23494-2:2026。

**对我们的直接用法**：我们的 `captured_at` / `published_at` / `body_source` / `body_url` / `run_id` / `record_type`
已经是一套**可用的 provenance 记录**，只是没有和标准对表。**不必现在做**，但「每条语料必须能回答：谁抓的、什么时候抓的、正文从哪来」这条纪律值得写进 `AGENTS.md`。

## 四、诊断与已实施的优化

### 4.1 用户问题一：「只收到文章的一小部分」——实测不成立

**口径**：1732 唯一条目，正文长度分桶。

| 分桶 | 条数 | 占比 |
|---|---|---|
| 无正文 | 73 | 4.2% |
| 1–119 | 37 | 2.1% |
| 120–199 | 34 | 2.0% |
| 200–499 | 259 | 15.0% |
| 500–1999 | 454 | 26.2% |
| 2k–10k | 621 | 35.9% |
| >10k | 254 | 14.7% |

**正文 <200 = 144 条 = 8.3%**；正文 ≥2000 字符占 **50.6%**。按渠道看正文均值：hn_show 6511、lobsters 9129、
hn_front 9674、devto 8263 —— **长正文渠道其实抓得很好**。

144 条缺口的**归属**（这是关键，不是总量）：

| 归属 | 条数 | 说明 |
|---|---|---|
| ① 已记死信账本 | 85 | 结构性（视频帖/账号页/反爬站） |
| ② 在回填队列 | 4 | 会被例行回填修掉 |
| ③ **无账可查** | **55** | bilibili 31 / apple_rss 18 / sspai 6 —— 既不在队列也不在死信 |

**「有 fulltext_url 但 body<200」= 真·可抓未抓 = 77 条**（hn_show 57 / reddit 20），主机分布：
`v.redd.it 15 / youtube 4 / github.com 4 / i.redd.it 4 / twitter 2 / play.google 2 / 其余长尾项目站各 1`。

→ **结论**：视频/商店/社交页（约 23 + 10 条）是结构性不可得；**真正可抓的长尾项目站个位数**。
**「只收到一小部分」不是本库的失败模式。**「Exa 截断」27 条 + 「RSS 摘要/残文」23 条才是真问题，且都已被标记、已入队列。

### 4.2 但发现了一个更严重的缺陷：**死信账本「判死得太早、理由还说错了」**

死信账本 270 条的判死理由分布（**取数 2026-09-21 修复前**）：

| 理由 | 条数 | 占比 |
|---|---|---|
| 取数失败（Exa 未命中该站） | 248 | 91.9% |
| 视频帖无正文 | 19 | 7.0% |
| 社交账号页需登录 | 3 | 1.1% |

**问题一：理由与实际流程不符。** 正文取数早已改成「`direct_fetch` 优先、Exa 兜底」，
但死信理由硬编码写「Exa 未命中该站」。**看账的人会得出「Exa 不行」的错误结论**，真实原因是
「直取被 `DIRECT_BLOCKED_HOSTS` 拦（news.ycombinator.com / github.com）+ Exa 也拿不到」。

**问题二（更严重）：判死时只走了一条后端链。** 死信 270 条里 **66 条目标 URL 是 `github.com/<owner>/<repo>`** ——
而 GitHub README **走 `api.github.com` 是本机唯一可达的通道**（`github.com` web 超时）。
它们没走这条链的原因是一个纯路由 bug：

```python
# tools/kb_backfill.py（修复前）
gh_items  = [(r, d) for r, d in todo if r["source_id"] == "github_new"]   # ← 按渠道分流
exa_items = [(r, d) for r, d in todo if r["source_id"] != "github_new"]
```

**路由键是 `source_id` 而不是 URL 主机。** 于是「非 `github_new` 渠道、但链接指向 GitHub 的条目」
（hn_show 里 66 条）全被分流到 `exa_items` → 直取被 host 黑名单拦 → Exa 拿不到 → **判死信**。
而 `fetch_github_readme()` **本来就支持从 URL 反推 `owner/repo`**，只是这些条目根本没被路由进去。
**这是纯路由缺陷，不是能力缺陷，也不是网络缺陷。**

修复时又发现第二个会「看起来生效、实际空转」的 bug：`fetch_github_readme()` 读 `r.get("url")` ——
对 hn_show 这类转发渠道来说那是 HN 帖子页，正则匹配不到 `owner/repo` → **静默返回空串**。
两处都改了，`github_target()` 按 URL 判定并把 URL 统一走 `body_target()`（优先 `fulltext_url`）。

### 4.3 用户问题二：「语料与预期不符」——分两类，语义类已解、**元数据类未解**

| 类型 | 表现 | 现状 |
|---|---|---|
| **语义类**（抓到的不是你想要的） | `reddit` 相关性可疑 89/244、`exa_discovery` 5/17、`v2ex` 5/34；讨论帖混进「项目」计数 | **已解**：2026-09-20 确立「契约型 vs 话题型渠道」判据 + `match: title` + `layer: signal` 分尺子；渠道画像矩阵已按 profile 判定 |
| **元数据类**（抓到的是你要的，但描述它的字段是坏的） | `published_at` 缺失 **107/1615 = 6.6%**，其中 `betalist 56 / indiehackers 43 / apple_rss 18 / c1c7 17 / xiaohongshu 1` **全部 100% 缺失**；另有 60 条 RFC822 未归一化、5 条字面量 `'N/A'` | **未解 → 本轮部分解决**（见 4.4） |

**为什么元数据类更严重**：本库明确声明的核心用例之一是「趋势/时间序列」，而趋势只能建立在 `pub_day` 上。
`betalist` / `indiehackers` 是**契约型渠道**（条目存在≈这是个项目），它们的 99 条**在时间轴上完全不可见**。
这不是「数据少一点」，是**这一类渠道的时间维度整体缺失，且不报错** —— 正是 §3.1 说的 metadata-borne defect。

### 4.4 本轮实施的优化（四项，全部经健康门验证）

| # | 改动 | 文件 | 证据 / 效果 |
|---|---|---|---|
| **1** | **发布日归一化**：新增 `kb_common.pub_day_of()`，把 ISO8601 / RFC822 / `2026/09/17` / `N/A` 统一成 `YYYY-MM-DD` | `kb_common.py`、`kb_collect.py`、`kb_navfix.py` | 消灭 `Tue, 17 Se` 这类**假时间分组**；`N/A` 归一为「无发布日」而不是写进 frontmatter。实测 `--dry` 报 `清坏pub_day: 5`，应用后归零 |
| **2** | **`set_fm_scalar(..., None)` 会写出字面量 `None`** → 新增 `kb_common.del_fm_scalar()`，值不存在时**整行删除** | `kb_common.py`、`kb_navfix.py` | 避免 Bases 里出现一个名为 `None` 的分组（比缺字段更糟） |

| **5** | **契约型无正文入账**：`kb_analyze` 新增 `expected_absent` 段（43 条：bilibili 25 / apple_rss 18），并写进 `analysis_latest.json` 与报告 | `kb_analyze.py` | 消灭「不在队列也不在死信」的账外条目；报表上「按契约没有」与「该有但没抓到」可区分 |

**验证（收工门）**：`kb_healthcheck.py` 八项 ——
① `20-语料 md=1615 == 在库唯一条目=1615` **OK** ② 应有项目页 1398 / 缺页 **0 OK** ③ 缺 url **0 OK**

**诚实记录（这条要说清，不要粉饰）**：GitHub 路由修复的**理论收益 66 条，实测只命中 6/22**。
原因是死信账本里的 `github.com` URL 并不都是仓库首页 —— 有些是 `…/tree/beta/apps/…` 这类子路径，

## 五、一句话结论

**本库的架构不需要改，需要补的是模式里被漏掉的那一半：结构性 lint 我们有八项，语义 lint 一项都没有。**
而这次用户问的「语料是否符合预期」，实测答案是：**内容侧（抓多少）健康，元数据侧（怎么描述它）在漏水** ——
而元数据缺陷正是最新论文里被反复点名、且**模型能力买不到的那一类**（SARC-DQ：跨越 15 倍推理价格的四个模型档，静默出错率保持平坦）。
