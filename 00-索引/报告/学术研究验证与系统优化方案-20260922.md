# 学术研究验证与系统优化方案

> **生成时间**: 2026-09-22  
> **依据**: Karpathy LLM Wiki 模式 + ArXiv/ACL/KDD论文调研（2026-04~09）  
> **核心结论**: ✅ **架构已命名且合理**；⚠️ **缺语义 Lint**是最大缺口

## 📊 **一、架构合理性验证**

### **与 Karpathy LLM Wiki 模式的对比**

| 模式要求 | 本库实现 | 状态 | 评价 |
|---------|---------|------|------|
| Raw sources 不可变，是唯一事实源 | `90-原始/<渠道>/<日期>.jsonl` | ✅ 完全一致 | **优于标准**（口径变化只加新字段） |
| Wiki 层由 LLM 生成并维护 | `20-语料` / `10-项目` / `30-人物` / `40-方法论` | ✅ 一致 | **更严**（有硬门禁，禁止手改） |
| Schema = AGENTS.md | 根目录 `AGENTS.md`（分层、字段、命令、六条红线） | ✅ 一致 | **粒度更细**（含具体执行纪律） |
| Ingest | `kb_collect` 流水线 | ✅ 超额 | **远超需求**（模式里是人工触发，我们是自动化） |
| Query | `00-索引/报告/` | ⚠️ **半实现** | 答案产出了，但没进检索面 |
| **Lint**（结构性） | 八项不变量 | ✅ 覆盖 | **超出标准**（计数/断链/漂移/合法性） |
| **Lint**（语义性） | ❌ **未实现** | 🔴 **最大缺口** | 页面间矛盾/过期论断/概念缺页 |

**结论**: ✅ **架构完全合理**，属于"独立收敛到同一解"的典型案例（5000+ star gist 的验证）。

### **问题诊断**

#### **问题 1: "只收到文章一小部分"是否成立？**

**实测数据**（分母=1732 唯一条目）:
```
正文 <200 字符: 144/1732 = 8.3%
├─ 已入死信账本：85 条 (结构性失败)
├─ 在回填队列：4 条
└─ 真·可抓未抓：仅 77 条
   └─ 类型：视频/商店页为主 (结构性限制)
```

**真实原因**: 
- ❌ **不是「抓得少」**，而是 **「判死得太早」**
- 死信账本 270 条中，**248 条的判死理由与实际尝试不一致**

**修复进度**: 
- ✅ 已修其中两类（见下文）
- ⏳ 剩余需结构化升级

#### **问题 2: 语义缺失导致的数据漏洞**

**当前结构性 Lint 覆盖**:
```
八项不变量全部通过：
✅ ① 语料数=在库数 (1615=1615)
✅ ② 缺项目页=0
✅ ③ 缺 url=0  
✅ ④ 断链=0
✅ ⑤ 路径漂移=0
⚠️ ⑥ 孤立语料=22 (软门)
✅ ⑦ suspicious project_url=0
✅ ⑧ 共用项目页=9 组 (正常归并)
```

**语义 Lint 缺失**:
```
❌ 无:
  - 页面间矛盾检测（同项目在不同语料里的指标冲突）
  - 过期论断识别（实体页观测历史 vs 页面正文不符）
  - 概念缺页发现（反复出现的赛道词没有赛道页）
  - 交叉引用缺失检查
```

**影响**: 元数据侧在漏水 —— SARC-DQ 论文指出，这是**模型能力买不到的缺陷**（跨越 15 倍推理价格，静默出错率保持平坦）。

## 🛠️ **三、优先级优化方案**

### **P1: 语义 Lint (架构级新增)** 🔴 **最高优先级**

**工具**: `kb_semantic_lint.py`（只读版先行）

**检测维度**:
```python
def semantic_check(items):
    # 1. 页面间矛盾
    conflicts = detect_conflicting_metrics(items)  # 同项目不同来源的数据冲突
    
    # 2. 过期论断
    stale_claims = find_obsolete_assertions(items)  # 观测历史 vs 页面正文不符
    
    # 3. 概念缺页
    orphan_concepts = identify_orphan_topics(items)  # 高频率出现但无独立页面的概念
    
    # 4. 交叉引用缺失
    missing_refs = check_missing_crossrefs(items)  # 应有关联但未建立 wikilink
    
    return {conflicts, stale_claims, orphan_concepts, missing_refs}
```

**产出**: 
- `00-索引/报告/语义 lint-YYYYMMDD.md`
- 不直接写页面，避免破坏现有结构

**工作量**: 2-3 天开发 + 1 天测试

---

### **P1: 死信账本结构化升级** ⚠️ **紧急修复**

**当前问题**:
```yaml
reason: "GitHub URL 无法访问"  ← 自然语言，不精确
```

**目标结构**:
```yaml
dead_entries:
  - url: "https://github.com/..."
    reason_code: http_404  # 标准化代码
    tried: 
      - direct_fetch       # 直取失败
      - github_api         # GitHub API 失败
      - exa_web_fetch      # Exa 兜底失败
    http_status: 404        # 实际 HTTP 状态码
    timestamp: "2026-09-22T14:00:00+08:00"
```

**判死前必须跑完的三档**:
1. `direct_fetch` (stdlib urllib, 首选)
2. `github_api` (若 URL 命中 github.com)
3. `exa_web_fetch` (兜底，免费额度会 429)

**工作量**: 1 天开发

### **P2: 元数据契约门** 

**实施思路**:
```yaml
# _meta/channels.yaml 新增 meta_unavailable 段
- id: betalist
  profile: linkpost
  meta_unavailable:
    published_at: "详情页 Featured 日期可用，但列表页无日期 → 结构性不可得"
    author: "产品列表页不含作者字段"
  params:
    pages: 3
```

**效果**: 
- 明确区分「结构性不可得」vs「真缺陷」
- 避免误报取数缺口
- 为自动回填提供准确线索

**工作量**: 2 天（逐渠道审核 feed）

### **P4: Query 答案归档**

**问题**: 报告产出但未进检索面，答案消失在聊天里

**规则建议**:
```
规则 1: 洞察报告 → 不进 wiki(时效性强，每日刷新)
规则 2: 内容审计 → 不进 wiki(操作指引，非知识结论)
规则 3: 重大发现 (跨渠道强信号≥3) → 可生成概念页
规则 4: 赛道分析方法论 → 应归档到 40-方法论/
```

**工作量**: 需先定规则，再实施（中风险）
