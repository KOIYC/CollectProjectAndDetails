# 信息组织与呈现：行业实践调研 + 本库诊断

> 起因：用户原话「基于当前的目录结构，我不知道应该怎么看」。
> 本文回答两件事：**① 行业里被反复验证的组织/呈现做法是什么；② 我们的库相对它差在哪、哪些已经做对了、怎么改。**
> 调研方式：agent-reach（Exa 网页搜索 / HN 公开 API / 中文社区），6 个来源，含 2 篇唱反调的观点。

---

## 一、结论：我们不是「组织得不好」，是缺了三个中间层

先说判断，再说依据。

**「不知道怎么看」这个感受，行业里有名字、有成因、有标准解。**

行业把这个问题归到 **information scent（信息气味）**：用户点不点一个链接，取决于他能否**在点之前**判断里面有没有他要的东西（Nielsen Norman Group）。点击成本一旦高于预期收益，人会直接放弃 —— 不是懒惰，是理性的信息觅食。

对照下来，我们的库有 **3 个真实缺口**：

| 缺口 | 具体表现 | 行业标准解 |
|---|---|---|
| **① 缺「按问题」的路由层** | 目录名 `00-索引`/`10-项目`/`20-语料` 是**内容类型**标签，不是**意图**标签。用户脑子里的问题是「我上次看到的那个定价讨论在哪」，目录回答的是「这里有语料」——两者对不上 | Diátaxis：文档结构必须按**用户需求阶段**（学 / 做 / 查 / 懂）组织，而不是按内容形态 |
| **② 缺 L1 目录层（机器可读的薄清单）** | 只有给人看的 `浏览.md` + Bases 视图。AI / 新会话每次进来要现扫 1689 个文件才知道库里有什么 | 四层模型：L0 源文件（唯一事实源）→ **L1 目录层（标题+摘要+路径，几十 KB，可整份塞进上下文）** → L2 检索 → L3 关系 |
| **③ 标签气味弱** | `[[浏览]]`、`10-项目`、`洞察-20260920` —— 名字本身不携带「点进去能得到什么」的信息 | NN/g 三大 IA 错误之一就是标签含糊；链接名必须**自解释**，不能靠上下文补 |

**同时，有 4 件事我们做对了，不该推翻：**

1. **文件夹只下潜 2 层**（`20-语料/posts/<渠道>/<日期>/`）—— 行业共识是「浅文件夹 + 标签」，深目录树必然产生归档摩擦。
2. **跨切面维度放属性、不放文件夹**（topic / kind / shard / pub_day + Bases 视图）—— 这正是「一个 note 只能属于一个文件夹」的解法。
3. **分层天然符合 medallion 架构**：`90-原始`（bronze，不可变）→ `20-语料`（silver，清洗后）→ 洞察/项目池（gold，面向消费）。
4. **归档可逆**（undo manifest）—— 行业里「归档」最常见的失败是「不敢删所以永远不整理」，可逆才敢整理。

| 5 | [NN/g：信息气味](https://www.nngroup.com/articles/information-scent/) + [3 个常见 IA 错误](https://www.nngroup.com/articles/3-ia-mistakes/) | 「人生太短，不够点开看不懂的东西」。链接**点之前**就要能判断去哪；含糊动词、并列语言、口语化标题都降低气味 | 直接命中 `[[浏览]]` 这个名字，和 `洞察-20260920` 这种纯日期标题 |
| 6 | [Obsidian 中文社区：文件夹/标签/双链](https://forum-zh.obsidian.md/t/topic/10730?page=2) + [双链与图谱实践](https://segmentfault.com/a/1190000048298678) | 三种**伪连接**：为连接而连接、双链当标签用、**没有索引层**。**全局图谱价值被严重高估**（「除了截图发朋友圈，很难读出有效信息」）；图谱是**体检工具**，每月打开一次找孤立点 | 我们有 5130 条 wikilink，但**从没跑过「孤立 note 体检」**。关系层建了却没消费方 |

**反调观点（必须收录，否则不诚实）**：[Personal Knowledge Management Is Bullshit](https://www.otherlife.co/pkm/)（HN 125 分 / 98 评论）。HN 高赞评论里最有价值的三条：

- 「**分享图谱截图的人基本是在自我营销**」—— 图谱是副产品，不是成果。价值在**写**的过程，不在**库**本身。
- 有人只用 **Windows 资源管理器 + 简单文件夹名**（work / car / medical），「找不到就用文件夹翻」——**够用就行**。
- 「**别过度整理，先扔进去**」—— 整理动作本身会变成拖延。

> **这条反调不是用来否定的，是用来设上限的**：组织的目标是「**能找回来**」，不是「**看起来整齐**」。
> 任何改动只要不减少「找不到」的次数，就是净成本。**本文的提案都按这个标尺排序。**

## 三、诊断：为什么你会觉得「不知道该怎么看」

拆成 4 个可复现的具体原因，不是感觉问题：

### 1. 入口页的首屏信息密度过高，且气味集中在后半段

`浏览.md` 的第一屏是：一段说明 + 6 行「想看什么→去哪」路由表 + **一个巨大的 8 视图 Bases 代码块**。
问题不在内容，在顺序：**Bases 代码块占据了视觉重心**，而它恰恰是「不知道怎么看的人」最不需要先看的东西（那是给已知道要找什么的人用的）。

行业做法（渐进式披露）：**首屏只放 3-7 个高层入口，其余一层点击可达**。

### 2. 路由表只覆盖了「读报告」，没覆盖「找东西」

现有 6 行路由全部指向**生成的报告**（洞察 / 修复报告 / 渠道台账 / 字段字典…）。
但用户真实的问题是另外四类：「**某个项目**在哪」「**原文**在哪」「**趋势**怎么看」「**我判错的**能不能捞回来」——这四类一个都没进路由表。

### 3. `10-项目/` 有 647 个页面，却没有地图

打开这个文件夹 = 面对 647 个文件名。Bases 视图能过滤，但**过滤是查询，不是导航** —— 查询要求你先知道自己在找什么。
行业标准解是 MOC：一个 domain 一个手动策展的索引页，**带叙事顺序和一句话说明**。我们一个都没有。

### 4. 机器侧同样没有地图

没有 `AGENTS.md` 或等价的薄清单。每次新会话（包括我）要理解这个库，都得现跑脚本、现扫目录 —— 这既是效率问题，也是**一致性**问题：不同会话可能得出不同理解。

## 四、提案：分三档，按「减少找不到的次数」排序

### A 档 · 今天就该做（低风险、纯增益、不动现有结构）

| 动作 | 具体做法 | 验收 |
|---|---|---|
| **A1 入口页重排** | `浏览.md` 首屏改为：**① 3 行「你现在想干什么」意图路由**（找项目 / 读原文 / 看趋势 / 复核归档 / 理解结构）→ ② 5 个关键数字 → ③ Bases 视图（折叠到下方） | 首屏不需要滚动就能看到 5 个意图入口 |
| **A2 命名提气味** | `浏览` → **`从这里开始`**（或保留页名但标题写明「找项目·读原文·看趋势·复核归档」）；报告改名为带信息量的形式：`洞察-20260920` → `洞察-20260920·AI工具占51%`（生成时自动加副题） | 随机抽 5 个链接名，能在**不点开**的前提下说出里面有什么 |
| **A3 加意图路由段** | 在路由表补上缺失四类：`10-项目/`（一个项目全历史）、`20-语料/`（原文+评论）、`80-归档/`（我判废的东西，可捞回）、`_meta/`（为什么这么判） | 四类真实问题各有明确落点 |

### B 档 · 值得做（结构性增益，需新增生成物）

| 动作 | 具体做法 | 验收 |
|---|---|---|
| **B1 补 L1 目录层** | 新增生成物 `_meta/catalog.json`（或 `00-索引/目录.json`）：每条 note 的 `标题 / 一句话摘要 / 路径 / 关键属性`，全库压到几十 KB。**由脚本从 frontmatter 生成，可随时重建** | 新会话能靠读这**一个文件**回答「库里有什么、某个话题在哪几条」 |
| **B2 加 `AGENTS.md`** | 根目录放一份「给 AI 看的入口」：库怎么分层、哪个是事实源、字段含义、常用命令、**哪些结论不能从这个库得出** | 新会话读完这一个文件就能正确使用本库，不需要先跑 4 个脚本 |
| **B3 三个 MOC** | `10-项目/索引.md`（按赛道分组的项目地图）、`00-索引/按问题.md`（Diátaxis 式的四类路由）、`80-归档/索引.md`（**误杀申诉入口**：归档理由分组） | 从入口到任意一条语料 **≤3 次点击** |
| **B4 报告标题去类别化** | 报告里的标题改成**陈述观点**而非类别。不写 `## 结论`，写 `## 跨渠道强信号只有 2 条，说明归并键缺失`（Minto：类别标题**没有扫描价值**） | 只读标题就能读懂报告主线 |

### C 档 · 需要先想清楚（有风险或依赖前置）

| 动作 | 风险 / 前置 | 建议 |
|---|---|---|
| **C1 验证「一条命令重建」** | 硬判据：删掉 `20-语料`，能否从 `90-原始` + `_meta/seen.json` 完整重建 710 条？**目前没验证过，且 `seen.json` 既参与去重又被当状态** | 先做**只读验证**（干跑重建到临时目录比对），再决定是否写进文档承诺 |
| **C2 归档区隔离** | `80-归档/`（289 md）在顶层可见，会分散注意力。行业做法是移出 content 树或加 `_` 前缀 | 移到 `_archive/`（Obsidian 里仍可搜到，但不与 4 个活跃目录并列） |
| **C3 孤立 note 体检** | 行业共识：图谱当**体检工具**，每月跑一次找孤立点。我们的等价物是 `kb_prune --liveness`，但它只针对实体页 | 加一条「孤立语料体检」进健康自检（⑥） |
| **C4 建向量/图检索** | **明确不建议**。几千篇规模下，L1 目录层已能解决大部分问题；建图成本是线性的十几倍（GraphRAG 论文：100 万 token 语料抽 8000 实体 + 2 万边），且每次更新要重跑 | 等目录层明显不够用（文档涨到数万篇）再说 |

| B4 报告标题陈述化 | ⏸ | 下轮报告起生效（待办 P3） |
| C1 重建验证 / C2 归档隔离 / C3 孤立体检 / C4 图检索 | ⏸ | C4 维持**明确不做**；C1-C3 进待办 P3 观察后决定 |

**实施中发现并修掉的一个检查器缺陷**：healthcheck ④ 不认 frontmatter `aliases`，
把 3 处有效链接 `[[从这里开始]]` 误报为断链（Obsidian 实际能解析）。已修：④ 按
**路径 + 文件名 + aliases** 三路解析，与 Obsidian 对齐。教训：**检查器必须和使用者一样宽，
否则它逼人写更差的链接文本。**

**另一个实施约束（写进待办）**：MOC 落在 `00-索引/` 而不是各自数据目录 ——
`10-项目/`、`20-语料/` 被计数脚本按 `*.md` glob，塞 index 页会把「647 个项目」变 648。

验收：`kb_healthcheck.py` 五项全绿（①710==710 ②缺页 0 ③缺 url 0 ④断链 0 ⑤漂移 0）。

## 六、一句话结论

**我们缺的不是组织纪律，是「意图 → 位置」的翻译层。**
行业里这个翻译层由三样东西承担：**入口页的低密度首屏**、**一层薄薄的目录清单**、**几张手工策展的地图（MOC）**。
三样都不动现有文件结构，都属于 A/B 档 —— 也就是说，**不需要重构，只需要补中间层**。

> **标尺提醒**（来自唱反调那篇）：如果改完「找不到」的次数没减少，就是白改。
> 建议 A 档先做，跑一周再看有没有真实改善，再决定 B 档要不要上。
